## P1 - GPU + LLM inference physics

**P1-B1 (basic)** LLM decode (generating one token at a time) is limited mainly by:

- a) GPU compute (FLOPs)
- b) GPU memory bandwidth
- c) PCIe bandwidth
- d) CPU speed

Answer: **b**. Each new token re-reads every weight (plus the KV cache) but does only ~2 FLOPs per weight per sequence. Arithmetic intensity ~= batch size, far below the GPU's ridge point.

Source: `ttg-agentic-genai-lab/docs/03-model-complexity.md`

**P1-B2 (basic)** Prefill (reading the prompt) is limited mainly by ____ and sets ____.

- a) bandwidth; inter-token latency
- b) compute; time to first token (TTFT)
- c) network; throughput
- d) KV cache; context length

Answer: **b**. Prefill processes all prompt tokens in parallel: ~2 x parameters FLOPs per token, compute-bound. It determines TTFT.

Source: `ttg-agentic-genai-lab/docs/03-model-complexity.md`

**P1-B3 (basic)** Llama 3.1 8B in BF16: about how many GB of weights? (8.03B parameters x 2 bytes)

Answer: **16.06 GB**. 8.03e9 x 2 bytes = 16.06 GB. FP8 halves it (~8 GB); NVFP4 roughly quarters it.

Source: `plv-multicloud-nim-lab/docs/00-recall.md`

**P1-I1 (intermediate)** Batch-1 decode floor for Llama 3.1 8B BF16 (16.06 GB) on an A100 80GB PCIe (1,935 GB/s), in ms per token?

Answer: **8.3 ms**. 16.06 GB / 1,935 GB/s = 8.3 ms per token (~120 tok/s per stream). The lab's selector adds a measured bandwidth-efficiency factor, so it prints a higher floor.

**P1-I2 (intermediate)** KV-cache bytes per token for Llama 3.1 8B BF16, in KiB? (32 layers, 8 KV heads, head dim 128)

Answer: **128 KiB**. 2 (K and V) x 32 layers x 8 KV heads x 128 dims x 2 bytes = 131,072 B = 128 KiB per token. An 8K-token conversation holds ~1 GiB.

**P1-I3 (intermediate)** Why is the L4 vetoed for Llama 3.1 8B BF16 at a 40 ms inter-token SLO?

- a) It has too little memory for the weights
- b) Its 300 GB/s bandwidth gives a ~53 ms decode floor
- c) It does not support BF16
- d) NIM does not run on Ada GPUs

Answer: **b**. 16.06 GB / 300 GB/s ~= 53 ms per token before any queueing: physics says no before anyone buys it. FP8 barely rescues it, and it is not on NIM's verified list for that model.

**P1-A1 (advanced)** H100 SXM BF16 ridge point: 989 TFLOPS / 3.35 TB/s = about how many FLOPs per byte?

Answer: **295 FLOP/byte**. 989e12 / 3.35e12 ~= 295. Decode at batch 1 runs at ~1 FLOP/byte, so batching (continuous batching) is the lever: throughput rises almost free until KV capacity or the compute roof stops it.

Source: `ttg-agentic-genai-lab/docs/00-recall.md`

**P1-A2 (advanced)** Llama 3.1 70B FP8 on 2x H100 80GB (TP 2): about how many 8K-token sequences fit in KV cache (BF16 KV, 320 KiB/token)?

Answer: **30 sequences**. Weights ~70.6 GB split across 160 GB leaves ~80 GB minus overhead for KV. 8,192 x 320 KiB = 2.5 GiB per sequence -> ~30 sequences (~60 with an FP8 KV cache). One H100 fits only ~2.

Source: `ttg-agentic-genai-lab/docs/00-recall.md`

**P1-A3 (advanced)** A customer asks: 'Which GPU should we run Llama 3.1 8B on, at 600 input / 200 output tokens and a 40 ms ITL SLO?' Walk through your method in 60 seconds.

**P7-A3 (advanced)** Describe the GB200 NVL72 in 60 seconds.
